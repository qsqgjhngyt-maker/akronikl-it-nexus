# Фотографии блога — кандидат транспорта BFF от 23 октября 2026

## Статус и цель

Это отдельный backend-кандидат. Он не опубликован в Yandex Cloud. Публикация frontend на GitHub Pages сама по себе не обновляет BFF. Область этого изменения — чтение частей фотографий между BFF и Worker; дополнительная регрессия поздней загрузки фото во frontend исправляется отдельным PR Alpha10.4.2.

Прежний код открывает отдельное TLS/HTTP2-соединение на каждый подписанный запрос части фотографии. Для синтетической фотографии размером 93 146 байт это 16 соединений и 16 RPC. Кандидат использует одно соединение в пределах одного чтения фотографии, не более четырёх одновременных RPC и закрывает соединение в `finally`. Публичное и приватное чтение используют разные соединения. Между HTTP-запросами соединения и фотографии не кешируются.

Каждая часть сохраняет отдельный подписанный envelope, nonce, request ID, действующую серверную проверку публикации или прав, проверку размера и SHA-256. Полный JPEG выдаётся только после проверки всех частей и полного SHA-256. При отмене, ошибке или отзыве прав соседние запросы останавливаются; частичная фотография не выдаётся. Загрузка новых фотографий сохраняет прежние два параллельных запроса и отдельное соединение на RPC. Cookie, CSRF, grants, приватный `no-store`, предел 12 секунд, admission и срок сессии не меняются.

## Проверенные результаты

Одинаковый native loopback TLS/HTTP2 стенд с настоящими подписанными BFF → Worker handlers и синтетической SQLite; Node 22.23.4 glibc; модель добавляет 100 мс на соединение и 80 мс на RPC:

| Вариант | Время чтения | TLS-соединения | RPC | Одновременно |
|---|---:|---:|---:|---:|
| Точный исходный транспорт | 2036 мс | 16 | 16 | 2 |
| Только повторное использование соединения | 993 мс | 1 | 16 | 2 |
| Кандидат: одно соединение и четыре чтения | 707 мс | 1 | 16 | 4 |

Это измерения синтетического стенда, а не обещание времени на живом сайте. Производственная задержка зависит также от BFF, Worker, сети и нагрузки. Доказательства исходных вариантов и SHA находятся в `docs/evidence/blog-media-transport-20261023/`.

Новый native regression: 11 проверок, включая 40 повторений отмены, сброса stream и отзыва публикации. Проверены отзыв публикации между частями (404), отзыв admin grant (403), независимость соседних public/private чтений, завершение всех socket/session, полная SHA-проверка и прежний 12-секундный timeout. Прежний native transport regression: 47 проверок, включая большие загрузки, 25 поздних отмен, TLS, HTTP2, ошибки заголовков, cookie/cache и ограничения ответов.

Тот же финальный код прошёл новые 11 проверок на Node 24.22.1. Локальный Node 24.19.0 воспроизводимо аварийно завершался при отзыве публикации и отмене соседних HTTP2 streams; точный native stack не получен, и конкретная upstream-причина не объявляется доказанной. Это не основание считать произвольный runtime проверенным. Текущий закреплённый Docker base содержит Node 22.23.3/Alpine для linux/amd64, что подтверждено SHA-проверенной OCI metadata. Обязательный финальный gate выполняет native tests именно внутри этого образа.

## Сборка и review

Workflow `.github/workflows/blog-media-read-transport.yml`:

1. Повторно собирает BFF из закреплённых зависимостей и требует совпадения с committed bundle.
2. Собирает прежний immutable Docker base, фиксирует image ID, commit, tree и фактический Node runtime.
3. Проверяет BFF, Worker и права на синтетических данных, затем оба native набора внутри production image с отключённой внешней сетью.
4. Проверяет прежнюю границу браузерного приватного кеша.
5. Только после успешных проверок упаковывает image tar и SHA256. Наличие артефакта после `if: always` не заменяет `SUCCESS` всего workflow.

Bundle SHA256: `8d6b1303337801569b2a17f7546b8062fc36aa917953ec240cadc8b6051eb11e`.
Base: `node:22-alpine@sha256:0a7108bf6c7bf5de370ffb1a3ed6be93d405b43ff159f681a8d18c0e2bc2e402`.
Никаких облачных credentials, database backup или действительных ключей в кандидат не добавлено. Worker, миграции, frontend, Docker base и публичные страницы BFF не меняются.

## Отдельный шаг доверенного оператора

Существующий порядок определён в `server-access/README_RU.txt` и `server-access/ALPHA10_OPERATIONS_RU.md`: GitHub собирает образ без автоматического deployment; облачную публикацию выполняет доверенный оператор.

Перед применением нужно получить текущие container/revision/image identifiers и подтвердить фактическое значение `BFF_CONTENT_MEDIA_PARTS_ENABLED`. Если parts-путь отключён, этот кандидат не ускоряет используемый старый путь; флаг нельзя включать без проверки соответствующего Worker-контракта. Существующая ревизия, переменные, service account, cookie ingress, лимиты, сеть и все девять pinned secret references должны быть сохранены. Секретные значения в чат и репозиторий не передаются. Миграций базы и изменения Worker не требуется.

Оператор проверяет commit/image/tar SHA, готовит ревизию с теми же параметрами и применяет только проверенный image. Затем сравниваются одинаковые публичные фотографии до/после, проверяются вход, доступ к управлению и загрузка фото с реальным подтверждением владельца. При проблеме возвращается точный предыдущий совместимый image с сохранением env и secret references; база не откатывается. До этих действий улучшение production transport не считается завершённым.
