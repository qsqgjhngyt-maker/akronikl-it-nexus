# ADR-AK0-001 — автономное ядро и подключаемые модели

Дата: 26.10.2026. Владелец реализации: **08 · INTELLIGENT ASSISTANT**.
Статус: архитектурное решение для AKRONIKL-0 implementation candidate; не разрешение на публикацию.
Исходный commit: `065606a788198045cadf250fea663246ddbb2d56`.

## Контекст

Владелец требует полезного помощника без интернета и API-ключей с дальнейшим подключением локальных и внешних моделей. В существующем Nexus есть legacy `akronikl/context.js`, передача контекста урока и кнопка помощника с planned-заглушкой. Legacy объект допускает произвольные patch-поля и не доказывает актуальность маршрута, кода или диагностик.

Помощник должен сохранять stable content IDs, прогресс, Code Studio, Nexus Account, ACL, HttpOnly и Cloud Sync. Есть пользовательские замечания к задержкам загрузки и навигации; новое ядро требует отдельного измерения влияния на эти сценарии. Производительность и учебный эффект будущего помощника пока не доказаны.

## Решение

1. Создать независимый от модели ESM Core с закрытым реестром возможностей, ограниченными контрактами, локальным поиском и предложениями навигации.
2. Получать контекст через доверенный адаптер Nexus. Использовать allowlist и независимые снимки; legacy context сопоставлять с фактическим маршрутом.
3. Привязать запрос к opaque boundary и epoch. На каждом переходе контекста, включая A → B → A, host меняет boundary и инвалидирует запросы.
4. Индексировать реальные публичные материалы репозитория воспроизводимой сборкой с происхождением фрагментов, версиями и SHA256. Отдельно готовить нужный язык и проверять его bytes/hash/version по доверенному manifest через `loadPreparedKnowledge`; reader передаётся host.
5. Определить единый `generate` для моделей. По умолчанию модели отсутствуют; внешние провайдеры заблокированы до AKRONIKL-3 и его security gate. В AKRONIKL-0 проверяется протокол с искусственным локальным адаптером.
6. Возвращать структурированные результаты и предложения. Тексты источников и моделей не могут предоставлять полномочия, регистрировать tools или запускать действия.
7. Сначала принять изолированное ядро; подключение к bootstrap/UI/PWA выполнить отдельным проверяемым этапом. Весь помощник развивается в ветке 08; MASTER 00 получает единый отчёт milestone и определяет межветочную маршрутизацию.

## Рассмотренные альтернативы

| Альтернатива | Причина отказа для первого этапа |
|---|---|
| Все функции через внешний AI API | Базовая полезность зависела бы от сети, ключей и доступности поставщика; усложнилась бы граница передачи данных |
| Загружать локальную LLM вместе с Nexus | Потребовались бы модельные assets, проверка устройств и нагрузка на старт до появления измеренного обоснования |
| Передавать legacy context модели целиком | Не обеспечены allowlist, актуальность, принадлежность данных и изоляция вложенных структур |
| Исполнять tools/URL, возвращённые моделью | Недоверенный текст получил бы влияние на действия приложения |
| Сразу строить адаптацию на Mastery/Learner Model | Фактические контракты и evidence этих подсистем ещё требуют подтверждения |

## Последствия и безопасность

Core можно проверить без подключённой модели и без сетевых вызовов. Смена провайдера не меняет capabilities или учебные IDs. Цена решения — отдельный host adapter, явный lifecycle и отдельная подготовка offline-ресурсов. Лексический поиск не заменяет свободное объяснение материала и может не найти смысловой эквивалент запроса.

Функции host и модели остаются доверенным кодом приложения. Frontend policy не заменяет серверную ACL и не изолирует произвольный JavaScript. Код и diagnostics передаются только в явно выбранном объёме при разрешении host и policy; это не гарантирует отсутствия секретов внутри выбранного текста. Внешняя передача в этом кандидате не выполняется.

Ядро не хранит диалоги, персональный профиль или код между сеансами. Индекс состоит из публичных учебных материалов. Для будущего BYOK отдельно потребуются разрешённый транспорт, хранение/отзыв ключей, ограничения адресов, минимизация контекста, пользовательское разрешение на передачу, лимиты и проверка утечек.

Hash-проверка защищает от несовпадения пакета с выбранной версией, но требует доверия к descriptor manifest. Текстовые метаданные курса/помощника сохраняют отдельные locale. Интеграционные helper-функции используют реальные форматы route, CodeWorkspace и parseRuntimeError, связывая выбранный код и диагностику с ревизией; подключение событий приложения остаётся отдельным этапом.

## Evidence и критерии принятия

Нужно сохранить: исходный SHA, changeset, реальные команды и результаты тестов, manifest/hash индексов, негативные проверки доступа/инъекций/смены контекста, дефекты и исправления, ограничения и способ воспроизведения. Наличие тестовых файлов не равно их успешному выполнению.

Материал для ВКР: отделение детерминированного ядра от модели, минимальный контекст, контроль жизненного цикла, provenance локального поиска, альтернативы и trade-offs. Возможные измерения следующего этапа: размер и время подготовки индекса, время поиска, задержка открытия помощника, влияние на навигацию, сохранность контекста при переключениях. До измерения это направления эксперимента, а не полученные эффекты.

## Интеграция и откат

Кандидат добавляет самостоятельные модули, индекс, сборщик, проверки и документацию. Существующие app/bootstrap, Identity, Cloud Sync, source content, progress/storage, service worker и production backend не требуется менять для проверки ядра.

Удаление/отклонение feature-кандидата не требует миграции пользовательских данных. Для будущего UI-включения нужны отдельный путь выключения, проверка cache transition и приёмка на устройствах. Merge в `main` и production остаются решением владельца.
