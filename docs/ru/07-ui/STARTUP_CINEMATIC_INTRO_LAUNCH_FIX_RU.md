# Исправление точки запуска заставки

STATUS: IMPLEMENTED / локальная браузерная приёмка PASS; новая публикация ещё не выполнена. Эта фиксация заменяет прежнее толкование «один раз после входа». Владелец уточнил: нажатие на иконку приложения или открытие ссылки в браузере должно начинаться с заставки, до авторизации.

Исходный main: `fa50859d5dcfa04181820fa2938dcb83cd0d3a45`. Для него подтверждены все 20 checks, включая Pages и полные M1–5. Работа ведётся в отдельной feature-ветке, исходники Content/08/Identity/Cloud/runtime и серверного BFF защищены побайтно.

## Причины и исправления

Прежний Intro устанавливался после Account/bootstrap, сохранял отметку просмотренной версии, отказывался от автопоказа при чужом focus/отсутствии Web Locks и закрывался при любом изменении дочерних узлов #app. При ожидании видео срабатывал слишком короткий fallback; число ядер и условная оценка сети также могли подменить видео секундным постером. Прежнее закрытие при перерисовке воспроизведено в Chrome на точной опубликованной сборке.

Теперь публичная страница запуска и приватная оболочка подключают независимый UI запуска, не ожидая Account. Каждый новый документ приложения показывает заставку, если пользователь её не выключил; старое поле seen больше не подавляет запуск. Переход авторизации в той же вкладке использует короткоживущую sessionStorage UX-подсказку и не включает второй ролик. Подсказка не является доказательством сессии и не влияет на auth gate. Её потребление и срок проверены отрицательными тестами. Проекты и другие ключи хранения не меняются.

Фоновый render, программный focus и bootstrap hash не закрывают видео. Скрытая при открытии вкладка ждёт видимости; смена окна ставит видео на паузу. Поворот меняет ролик с сохранением относительного прогресса. Длительность штатного показа определяется реальным ended: Desktop 10 секунд, Mobile 8,033 секунды. Кнопка «Пропустить» сохраняет opacity0.55, клавиатурный доступ и немедленное завершение. Предусмотрены ограниченные сетевые сроки ожидания, reduced-motion, экономия трафика и offline fallback.

## Новый widescreen и переходы обоих роликов

Выбран именно файл владельца `b0ccd1a80ebc4c32815570afb633a8c8.mp4`, найденный в Downloads: SHA256 `21fdd3ae2d9bbcbcbb142adcd9a45c17a47b71a63c80c54c790e032cb5cf4108`. Исходный размер 61 354 774 байта; 1920×1080, 16:9, 30 fps, 300 видеокадров = 10,000 секунды. Контейнерные 10,03 секунды включали хвост аудио. Все 300 кадров сохранены, звук удалён. Оптимизированные MP4 Main4.0 — 2 298 868 байт; WebM VP9 — 2 115 097 байт; постер финального кадра — 124 139 байт. Оба формата полностью декодированы, 300 кадров/10,000 секунды. Это оставляет запас к документированному [лимиту ответа API Gateway 2,5 МБ](https://yandex.cloud/en/docs/api-gateway/concepts/limits), без изменения Gateway или CSP.

Мягкое проявление видео длится 1200 мс. После настоящего ended финальный кадр остаётся 500 мс, затем видео затухает в тёмный фон за 900 мс и сам фон открывает готовый интерфейс за 500 мс. Источник video сохраняется до завершения затухания, поэтому последний кадр с логотипом не теряется. Дополнительный логотип и подпись поверх видео отсутствуют. Mobile получает те же переходы; его MP4, WebM и постер побайтно прежние. Полный обычный цикл с завершением занимает примерно 11,9/9,93 секунды плюс получение первых кадров; «Пропустить» доступно сразу и во время завершения.

Сборка shell и Account не ожидает ни media, ни этих переходов. Время просмотра сознательно увеличено по пожеланию владельца; оно не является временем загрузки приложения. Лабораторные парные измерения и ограничения перенесены в evidence, полевой perceived performance не объявляется доказанным без проверки устройства владельца. В обязательный install SW ролики не включены, проверка квоты/согласие на их сохранение не обходятся.

Настройки помещены в общее меню режимов и диалог оформления у всех пользователей, без проверки административных прав. До входа доступны «Настройки запуска». Из Account/административного раздела отдельная панель удалена. Ручной preview открывается поверх других диалогов и не меняет прогресс или вход.

## Доставка до входа и граница разрешения

Рабочий root без сессии выдаёт страницу старта из существующего контейнера BFF. Одних файлов GitHub Pages для подключения к ней недостаточно. Подготовлен ровно один новый браузерный файл `/app/public/entry.js`: он независимо загружает публичный same-origin descriptor `/startup-intro.json`, проверяет схему и фиксированный путь module и подключает UI. До публикации descriptor его404 безопасно оставляет прежний вход. Последующие изменения заставки будут доставляться обычными статическими файлами.

Локальный образ собран FROM точного активного production image `sha256:f1fc8e6faf945d12295a28ea0c72af394e756f4a59c307b5aa65cd942a75ced1` с единственным COPY браузерного entry.js. Локальный образ: `nexus-intro-launch-ui:20261028`, digest `sha256:526ba85d3acbe167b33dd750257807c7017900c0e7667212801465278dff10ab`. Ни registry push, ни новая облачная ревизия при этой фиксации не выполнялись.

Исходное поручение владельца запрещает изменение BFF без отдельного разрешения. Владелец дал его в текущем разговоре: «Да, обновить только UI запуска», затем подтвердил выполнение необходимых проверок. Разрешение относится к одному браузерному entry.js; серверный код, auth/session/OAuth, IAM, Gateway, Worker/D1 и параметры ревизии сохраняются.
