## Предлагаемая роль Module 6

Рабочее название: «Событийные приложения: от модели до интерфейса». Сохранить существующий `cpp.visual-event-model`, legacyIndex39/order40. Из 12 предлагаемых тем 10 составляют проверяемое ядро и две посвящены настоящему графическому приложению внутри Nexus. Окончательный объём M6-1 требует решения владельца. Механически ограничивать модуль прежней единственной темой недостаточно.

M6-A/X — редакционные ключи, не stable IDs. Машинный DAG, ввод понятий до использования и лабораторные находятся в `CPP_MODULE6_DEPENDENCIES.json`. Для каждой будущей темы нужны полные RU/EN материалы: результаты и предварительные знания, подробная теория, разобранные примеры, типичные ошибки, контрольные случаи, задания с постепенным снятием scaffold, лабораторная, рубрика и связь с итоговым приложением. Новые конструкции `std::function`, `std::variant`, `std::visit`, weak_ptr и кооперативная отмена должны объясняться до самостоятельных задач.

В текущем Code Studio проверено консольное событийное ядро. Qt, Windows Forms/C++CLI и OS threads там не допущены. Консольный вызов `onCalculateClick()` нельзя называть работающим графическим приложением. Отсутствие Qt не является ошибкой стандартного C++: это дополнительная библиотека и инструментальная цепочка.

Для настоящего GUI требуется встроенный target Nexus и Preview проекта учащегося. Первый кандидат для проверки — Qt/WebAssembly: [официальная документация](https://doc.qt.io/qt-6/wasm.html) описывает браузерный запуск через отдельную Qt/Emscripten toolchain. Это ещё не рабочая интеграция; новый runtime должен пройти C++20/EH, mobile, accessibility и NEXUS-PERF-01 gate. Внешняя установка Qt не заменяет выполнение задания в Nexus.

Полный цикл: создать проект → редактировать → собрать → запустить настоящее приложение → выполнить тесты → сохранить → сдать точную ревизию → получить оценку и исправить ошибки внутри Nexus. Для переносимости нужен обычный архив исходников, ресурсов, тестов и CMake/инструкций; сборка вне Nexus — дополнительный маршрут. Текущий .nexus.json сам по себе ещё не доказывает готовность такого архива.

Ограничения M6-0 переводятся в задачи студии, а не в обязательный переход студента во внешнюю IDE. Детальный backlog и критерии: `CPP_MODULE6_NEXUS_RUNTIME_PLAN_RU.md`; новое машинное требование `CPP_MODULE6_NEXUS_REQUIREMENTS.json` имеет приоритет над прежним guiDecision/внешней трактовкой extensionTopics в первоначальном DAG. Готовая JavaScript-демонстрация не заменяет компиляцию C++ учащегося и живую обработку событий.

## Проекты и стартовые наборы

Опора — уже существующие направления `tasks` (TaskFlow), `finance` (домашняя бухгалтерия), `logs` (LogScope), а также склад/CRM по выбору. Новые финальные задания должны расширять эти направления, сохраняя прежние project IDs, код и работы пользователей. Здесь они не изменены.

Рекомендованные варианты: TaskFlow с моделью статусов, фильтрами и историей команд; финансовый реестр с проверкой сумм, отчётами и версией формата; LogScope с разбором повреждённых строк, статистикой и ограниченной очередью событий. Консольный адаптер и VFS полезны для тестирования модели. Если проект требует GUI, его выполнение и проверка должны проходить внутри Nexus после допуска нового runtime; консоль не заменяет эту часть. Реальные платежи, серверы, авторизация и сетевые API не нужны для доказательства этих результатов.

«Предсобранный» проект лучше дать как стартовый набор: структура каталогов, интерфейсы, TODO, небольшие синтетические данные, публичные тесты, инструкция запуска и критерии готовности. Ведущий разбор решает маленький аналог, а основную логику пишет учащийся. Возможны три равноправных маршрута: заполнить scaffold; реализовать по спецификации; предложить свой проект с согласованными результатами. Уровень поддержки отличается, итоговая рубрика общая. Полностью готовый проект для копирования не проверяет самостоятельность.

Этапы сдачи: требования и критерии → модель/инварианты и план тестов → работающий прототип → обработка ошибок и граничные случаи → рефакторинг, README и воспроизводимый запуск → защита с новым небольшим требованием. На каждом этапе нужна содержательная обратная связь, а не только зелёная кнопка запуска. Публичное портфолио — по выбору владельца работы, без автоматической публикации личного кода.

Предлагаемая рубрика проекта: корректность и граничные случаи30%; тесты и диагностика20%; владение ресурсами/RAII и безопасность15%; архитектура и читаемость15%; выбор структур и объяснение сложности10%; воспроизводимость, документация и демонстрация10%. Ошибки lifetime, потеря состояния или невоспроизводимая сборка требуют исправления. Эти веса также подлежат пилоту.
