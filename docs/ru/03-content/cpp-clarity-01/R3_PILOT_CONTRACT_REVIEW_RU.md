## Предложение для решения 01

Только allowlist трёх canonical topic ID: cpp.programming-process, onec.p2.topic-1, onec.p7.topic-2. Только существующий account adapter либо явно разблокированная локальная копия. Ни нового unscoped browser key, ни endpoint, ни server sync, ни нового шифрования или Identity transport.

Предлагаемое место: дополнительное lesson-поле clarityDraft в существующем course store соответствующего курса. C++ — courses.cpp.lessons[id].clarityDraft;1С — lessons[topicId].clarityDraft в прежнем onec-candidate:v1:onec. Изменение1С-store потребует отдельного точного разрешения пути в preservation и review, а не выключения защиты дерева. Курс1c-enterprise и прежние данные не трогаются.

Предлагаемая закрытая схема clarityDraft v1:

- schemaVersion:1; contentRevision — явная редакция согласованного материала, одинаковая по смыслу для RU/EN; stateRevision — монотонная ревизия записи.
- stage из explanation/selfcheck/practice; позиции трёх этапов; activeFile/cursor — только ссылка на действующий workspace, без второй копии текущего кода.
- answers по трём известным questionId: value, checked, contentRevision. Свободный ответ не оценивается. Изменение ответа сбрасывает checked. При новой редакции старый текст сохраняется, положительный checked не переносится автоматически.
- workBinding: existing project/workspace ID + ожидаемая ревизия. Никакого автоматического проекта при чтении/переходе/смене языка. Нет workBinding — можно пройти BSL во внешней1С и записать самоотчёт без Studio.
- reportDraft и lastResult отдельно. lastResult.kind — runtime либо external-self-report; sourceDigest, stdinDigest, sourceRevision, output и признак актуальности. Самоотчёт никогда не становится серверной проверкой. При внешнем BSL браузерный snapshot явно не доказывает фактически выполненный модуль.

Предлагаемые пределы требуют решения01/02: максимум3 записи по allowlist; по4096байт UTF-8 на свободный ответ;16384байта на текст результата;до32768байт на ограниченный снимок источника результата; всего clarityDraft не более65536байт на тему. Это локальные пределы нового поля, не увеличение прежних runtime/performance/vault caps. Если собственный workspace превышает допустимый snapshot, его прежнее сохранение остаётся доступным; запись полного снимка результата отклоняется с явным сообщением и возможностью выгрузки, исходник не обрезается. Не удалять старые данные ради лимита; schema conflict/corruption требует сохранения исходного значения и отдельной диагностики.

Вопрос01 для решения: допустимы ли эти места/поля/пределы в текущей границе Account и локальной копии; можно ли включить сохранение таких ответов без новых прав/ключей? Нужны явные ограничения на неподтверждённый контекст, смену аккаунта, конфликт/повреждение и незавершённую запись.

## Предложение для решения 02

Один активный буфер сохраняется до ухода из темы. Для C++ — getSnapshot текущего bindCodeStudio + stdin; изменение файла не пересоздаёт исходник по примеру. Для необязательной1С-работы — существующий saveOnecWork(expectedLocalRevision); внешний Конфигуратор остаётся главным маршрутом без обязательного промежуточного Studio.

Переход между тремя этапами предпочтительно меняет видимость представлений в пределах одной смонтированной темы. При фактическом размонтировании/смене темы/языка: синхронизировать буфер → проверить тот же account/local-session и текущую ревизию → сохранить через выбранный adapter → дождаться подтверждения → сменить маршрут. Ошибка quota/lock/conflict не должна выбрасывать буфер и не должна показывать «сохранено». Отмена оставляет текущую работу; явный экспорт доступен отдельно. Нельзя полагаться только на beforeunload как механизм завершения async-записи.

Результат привязан к точному source+stdin, а не только к номеру версии, который может совпасть в другой вкладке. Для ограниченного снимка используется канонический порядок путей и точные байты. Новый ответ runtime относится к захваченному запуску; после правки или смены контекста он не помечает новую работу успешно выполненной. Проверка свойств программы остаётся штатному runtime; BSL не эмулируется в JS.

Вопрос02 для решения: подтверждаете ли переиспользование перечисленных workspace API и политику flush/ошибок/ревизий; где хранить ограниченный snapshot результата без конкуренции с checkpoint? Для кода свыше предложенного лимита выбрать явный отказ либо ссылку на существующий подтверждённый checkpoint. Ни старые проекты, ни snapshots не удаляются.
