## Новый отправитель Mail.ru

Служебный ящик: `<служебный-адрес>`. Получатель испытаний: `<тестовый-получатель>`.
Пароль входа в почту приложению не нужен: создайте отдельный пароль приложения
«Nexus Staging» по [инструкции Mail.ru](https://help.mail.ru/mail/login/mailer/).
Настройка выполняется локально:

```powershell
powershell.exe -NoProfile -STA -File server-access/staging/configure-mailru.ps1 -StateDirectory <private-state-directory>
```

Окно маскирует пароль. Скрипт записывает его в закрытый файл staging с ACL
текущего пользователя и SYSTEM, без вывода и без аргументов командной строки.
После перезапуска BFF режим станет `live`, провайдер `mailru`. Письма разрешены
ТОЛЬКО на заранее заданный тестовый email; публичного выбора адресата нет.
Нужны SMTP implicit TLS к `smtp.mail.ru:465` и проверенный сертификат.
SMTP и исходящий staging RPC используют IPv4: на операторском компьютере
автоматический выбор маршрута давал зависания. Проверка TLS не отключается.
Общий бюджет mail-операции — 15 секунд, SMTP — до 10 секунд, нейтральный
ответ отправляется через 15,5 секунды, включая запросы неизвестных адресов.
Resend также поддерживается, но отдельный аккаунт/домен для варианта Mail.ru
не требуется. SMTP ключ для будущего production должен быть отдельным и лежать
в secret manager; этот локальный staging файл не переносить в production.

После отправки проверить `delivery-status.json`: `accepted` означает, что SMTP
сервер принял письмо. Затем получатель отдельно подтверждает получение, в том
числе проверяет папку «Спам». Коды вводятся только в форму staging, не в чат.
При отказе сохраняются только технический код, номер SMTP и фиксированная
категория (например, `spam-policy`), без текста ответа провайдера. Успешная
авторизация SMTP сама по себе не доказывает приём письма. Отказы 550 требуют
отдельной проверки отправителя/политики Mail.ru; не обходить антиспам повторной
массовой отправкой и не сбрасывать лимиты приложения ради приёмки.

## Воспроизводимость

Сборка без облачных изменений:

```text
npm ci --prefix server-access --ignore-scripts
node server-access/build-worker.mjs
node server-access/staging/build.mjs ../staging-build
node --test server-access/staging/security.test.mjs
```

Новый отдельный стенд (не повторять для уже созданного):

```text
node --experimental-sqlite server-access/staging/cloud.mjs create <new-private-directory> <test-email>
```

Команда создаёт только новый staging name/DB и отказывается перезаписывать
существующий manifest. Она не копирует production данные или секреты.
Перед созданием нужен действующий `wrangler whoami`. IAM для Yandex тут не используется.

Локальный запуск:

```text
node server-access/staging/start.mjs <private-state-directory> native
```

Переменная NEXUS_STAGING_NODE должна указывать на проверенный Node 22 executable;
NEXUS_STAGING_BUNDLE — на собранный runtime, если используется другая папка сборки.
Запускается скрытый отдельный процесс, bind 127.0.0.1:8443. Альтернатива — Docker
image из staging Dockerfile, port publish только 127.0.0.1. Docker может не иметь
сетевого доступа в конкретной локальной среде.

`smoke.mjs` — воспроизводимая первичная capture-приёмка нового стенда с ещё не
принятым fixture приглашением; она расходует приглашение. Её нельзя повторять
как бесконечный reset пользователей. Дальнейшая приёмка выполняет recovery
тестового аккаунта с соблюдением лимитов. Приложение не содержит режима их обхода.

Синтетический fixture administrator служит только bootstrap стенда; он не является
проверкой настоящего владельческого Passkey. Контроль fresh Passkey/ACL проверяют
профильные регрессии. Не использовать fixture или staging DB для production.

Остановка: остановить только PID/контейнер, созданный этим staging, после проверки
его пути/label. При удалении облачного стенда сначала сверить имя и DB UUID с
manifest; production IDs запрещены validateStage. Удаление ресурсов автоматически
не выполняется, поскольку владелец может продолжить приёмку.

## Приглашения

Старые неотозванные, неиспользованные приглашения с действующим сроком остаются
Passkey-приглашениями. Для нового email+password onboarding создаётся новый invite
с email. Не перевыдавать массово приглашения уже зарегистрированным пользователям:
сейчас новый invite создаёт новый Nexus Account; перенос старого прогресса или
добавление пароля существующему аккаунту не входит в этот onboarding.
